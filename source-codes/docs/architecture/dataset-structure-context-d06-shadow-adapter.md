# Dataset Structure Context — D06 cadence shadow-adapter contract

**Status:** documentation-only post-Observed-Cadence design contract. It changes no producer, resolver endpoint, D06 methodology, manifest, API, UI, readiness, finding, or AAR-artifact behaviour.

**Consumer:** `T2-D06` Row-completeness reconciliation.

## Outcome and ownership

This is a D06-owned, fail-open observation of an already-materialised DSC cadence assertion. It uses D06's frozen `RunScope`, but is scheduled only after D06 has successfully completed its authoritative runner writes: reconciliation, results, findings, and AAR persistence. D06 reports are lazily generated by `report_payload()` after runner completion and are outside this scheduling transaction. The shadow may then compare the frozen reporting-grain configuration with the one exact DSC axis/grouping pair selected by the frozen period and facility columns.

DSC owns assertion evidence and projection. D06 owns facility and reporting-period meaning, reporting grain, scope confirmation, reconciliation, findings, readiness, manifest, UI, and reports. The observation never selects a different axis, entity, grouping, grain, role, or reporting grain. It creates no DSC assertion or decision; does not change a frozen role; does not create a finding, gate, prompt, or disposition; and does not make cadence a D06 requirement.

In particular, DSC cadence is observed structure, not declared reporting meaning. Parser acceptance/count differences between D06 and DSC are advisory implementation evidence only, never a D06 defect or automatic discrepancy.

## Invocation and immutable input

After D06's reconciliation, result/finding persistence, and AAR writes have completed successfully, the runner captures the already-frozen immutable input below and may schedule one best-effort daemon/background shadow task before returning. Lazy report generation is not a prerequisite for scheduling and must remain byte-identical whether it occurs before, after, during, or without a completed shadow task. The runner returns immediately after safe thread preparation/start and never joins or waits for scheduling, projection, comparison, metric, or audit completion: D06 has zero synchronous shadow latency and no background SQLite read can contend with a D06 writer. The task receives only this immutable frozen-run projection plus a mandatory trusted `tenant_id`:

```json
{
  "run_id": "drun_…",
  "manifest_fingerprint": "<sha256>",
  "snapshot": {"asset_id": "…", "snapshot_id": "…"},
  "scope": {
    "table": "…",
    "facility_id": {"table": "…", "column": "…"},
    "period": {"table": "…", "column": "…"},
    "reporting_grain": "monthly|quarterly|semiannual|annual"
  }
}
```

The selected pair is mechanically exact:

```json
{
  "predicate": "table.temporal/observed_cadence",
  "table": "<scope.table>",
  "axis_id": "column:<scope.period.column>",
  "axis_column": {"table": "<scope.table>", "column": "<scope.period.column>"},
  "grouping": [{"table": "<scope.table>", "column": "<scope.facility_id.column>"}]
}
```

The grouping array must have exactly one member. D06's optional segment is intentionally absent: it is neither a cadence grouping nor a shared segment claim in this increment. Any assertion for another period axis, facility grouping, composite grouping, table, or snapshot is outside the request rather than an alternative to select.

The adapter cannot mutate this projection, the persisted frozen manifest, `diag_runs`, decisions, D06 reconciliation identity inputs, source-artifact references, or `manifest_fingerprint`. Its result is not passed to the reconciliation engine. Snapshotting immutable inputs, constructing the daemon thread, and starting it are each independently caught and fail-open; a preparation/start error writes no D06 state and does not change the completed D06 response. The direct adapter function remains synchronously callable only for unit/integration tests; production execution uses the daemon/background scheduling seam.

## Public side-effect-free projection seam

The adapter must not use the normal resolver request/envelope path. It calls a new public `analysis_runtime` seam named `project_materialized_dataset_structure`, whose only purpose is a non-mutating read of already-active DSC materialisation.

The normalized input is the frozen asset/snapshot/table and the exact selected pair above, with `consumer_id: "diagnostic:6:dsc-cadence-shadow-v1"`. The seam admits exactly one table, one predicate, one axis, and one single-column grouping. It rejects a caller that broadens any selector. It is not a general search or candidate-ranking API.

The seam opens one consistent AAR transaction and returns a structured `resolved_as_of` marker. It contains the transaction timestamp and `read_boundary_fingerprint`, the SHA-256 of canonical ordered records for every exact selected assertion/dependency artifact (`artifact_id`, payload hash, repository status, lifecycle) plus the relevant selected-snapshot/table catalogue-or-lifecycle event marker observed in that same transaction. Callers cannot provide a historical value or stitch results from separate reads. The seam verifies canonical payload hashes and active same-snapshot lifecycle in that transaction, without writing or recalculating any artifact. It must not use `PRAGMA data_version` as a consistency marker. The returned response has closed identity `{projection_version:1, request_identity:<canonical exact-pair digest>, resolved_as_of:<timestamp+read_boundary_fingerprint>}` and no free-text field.

Its bounded result is one of:

```json
{
  "projection_version": 1,
  "request_identity": "<sha256 exact-pair request>",
  "outcome": "fulfilled|selected_pair_absent|unavailable|ambiguous|error",
  "resolved_as_of": {"timestamp": "<transaction timestamp>", "read_boundary_fingerprint": "<sha256>"},
  "reason": "dependency_changed|dependency_limit_exceeded|source_missing|source_integrity_failed|payload_limit_exceeded|evidence_limit_exceeded|invalid_response|deadline_exceeded|db_busy|projection_error|null",
  "cadence": {
    "resolution_state": "observed|confirmed|unknown",
    "value": {"state": "regular|mixed|irregular|unknown", "observed_interval_class": {"unit": "…", "step": 1}},
    "assertion_pin": {"artifact_id": "art_…", "payload_hash": "<sha256>", "dependency_fingerprint": "<sha256>"}
  }
}
```

The `cadence` object/pin is available only to the in-process caller and any separately authorised audit transport; it is never a general log/metric payload. A regular state alone may carry the closed interval class. Candidate lookup uses `SQL LIMIT 5`: up to four active **cadence assertion rows/candidates** at the exact locator are evaluated and a fifth makes the result `ambiguous`. It never truncates to a winner, retries, chooses by recency, or scans other candidates.

The assertion-row cap does not cap or replace dependency verification. For every candidate examined, the seam validates every declared dependency reference, including the current producer's six references. `MAX_D06_DSC_CADENCE_SHADOW_DEPENDENCIES` is 16 declared references per candidate; `MAX_D06_DSC_CADENCE_SHADOW_PAYLOAD_BYTES` is 262,144 canonical bytes; and `MAX_D06_DSC_CADENCE_SHADOW_EVIDENCE_RECORDS` is 8. Exceeding a dependency, payload, or evidence cap is `unavailable` with the applicable closed limit reason, not a partial projection; a missing, tampered, non-active, cross-snapshot, or hash-mismatched declared reference is likewise `unavailable`. The seam never omits a dependency or evidence record merely to satisfy a bound.

It performs no context-envelope write, assertion write, AAR lifecycle/status update, event/audit write, source-profile read, raw-table read, producer call, observation, inference, supersession, cache refresh, or retry. A detected missing/tampered/non-active pin, an active lifecycle change within the consistent projection, or a dependency fingerprint mismatch returns `unavailable` with `dependency_changed` (or the applicable closed integrity reason). It does not retry against a newer state.

## Confirmation, unknown, and competing semantics

The seam applies DSC's authoritative resolution only at the exact requested locator.

- A sole valid observed assertion for the pair projects as `observed`.
- A sole valid `confirmed` assertion projects only when it confirms the identical axis, grouping, observed cadence value, and dependency fingerprint of its active observed assertion. Confirmation does not declare expected frequency or replace the observation.
- A retained completed-scan `unknown` assertion projects as `unknown` only when full cadence-producer provenance can be reconstructed: it is a validated `table.temporal/observed_cadence` producer assertion with its required bounded-scan evidence, exact axis/grouping locator, all declared role/table/axis/grouping/profile dependencies, active same-snapshot hashes/lifecycle, and allowed `DSC_R_INSUFFICIENT_BASIS` reason. It means insufficient structural basis, not irregularity and not absence. Missing or invalid producer evidence/provenance is `unavailable`, never accepted as `unknown`.
- No matching locator is `selected_pair_absent`; this is distinct from a materialisation/source/integrity failure (`unavailable`).
- Competing valid observations, confirmations, or a confirmation that disagrees with the observed value/dependency are `ambiguous`. They are never resolved by authority, timestamp, confidence, D06 reporting grain, or another candidate.

The caller treats a result from a different asset/snapshot/table, a non-canonical payload hash, or a missing `resolved_as_of` as `unavailable`, not as a cadence outcome. No assertion ID/hash is incorporated into D06 identity or persisted D06 state.

## Closed comparison outcomes

The adapter returns exactly one of these closed observational outcomes:

| Outcome | Exact rule |
| --- | --- |
| `supports` | The exact pair is regular and its class is equivalent to the frozen D06 reporting grain. |
| `different_observed_interval` | The exact pair is regular, has a class in the comparison map, and it is not equivalent to the frozen D06 reporting grain. |
| `non_regular` | The exact pair is mixed or irregular, or is regular but its class is outside the comparison map. It is advisory/non-comparable, not a violation. |
| `unknown` | The exact pair projects an `unknown` completed-scan state. |
| `selected_pair_absent` | No already-materialised assertion exists at the exact selected locator. |
| `unavailable` | Projection cannot safely establish the exact same-snapshot/hash/lifecycle basis, including `dependency_changed`. |
| `ambiguous` | Competing assertions or confirmations exist at that exact locator. |
| `error` | Timeout, seam exception, result-validation error, or telemetry error was contained. |

The only interval equivalences are exact closed objects:

| Frozen D06 `reporting_grain` | Supporting DSC regular class |
| --- | --- |
| `monthly` | `{unit:"month",step:1}` |
| `quarterly` | `{unit:"quarter",step:1}` or `{unit:"month",step:3}` |
| `semiannual` | `{unit:"quarter",step:2}` or `{unit:"month",step:6}` |
| `annual` | `{unit:"year",step:1}`, `{unit:"quarter",step:4}`, or `{unit:"month",step:12}` |

Every other regular class, including day/week intervals, is `non_regular` with comparison basis `advisory_non_comparable`. It must not be labelled a mismatch. `different_observed_interval` is a structural observation only and cannot change D06 execution, readiness, findings, verdict, or report.

## Bounds and failure isolation

The production daemon/background worker has a cooperative `MAX_D06_DSC_CADENCE_SHADOW_WALL_MS` deadline of 2,000 ms from start through best-effort telemetry submission and `MAX_D06_DSC_CADENCE_SHADOW_DB_BUSY_TIMEOUT_MS` of 100 ms. The 100 ms limit includes database connection acquisition, feature-flag lookup, projection, and audit insertion; it is not merely a query busy pragma. The projector opens a read-only bounded SQLite connection under WAL mode; it cannot acquire a writer lock. It has one projection call, one consistent AAR read, zero retries, zero producer calls, zero direct snapshot loads, and no child work. It may abandon a projection, metric, or audit attempt on deadline, database contention, or process exit. The deadline is cooperative/background only and cannot affect completed D06 work or the runner return path.

The scheduler has no global worker lock. Any process-local in-flight marker is keyed by `(tenant_id, run_id, adapter_version)`, expires no later than the cooperative deadline, and is released in a `finally` path; a stalled daemon cannot indefinitely suppress a later shadow run (including one for a different run ID). The runner never waits for the worker. The adapter makes no projection call when its flag is off.

Every exception, timeout, malformed response, lifecycle change, database-busy result, process exit, and telemetry fault is contained at the worker boundary. The D06 reconciliation continues through the unchanged existing path exactly once. A shadow result can neither make an existing reconciliation artifact reusable/non-reusable nor delay, cancel, annotate, or join its computation.

## Configuration

Enablement is tenant-scoped and uses the existing `tenancy.is_flag_enabled(tenant_id, "D06_DSC_CADENCE_SHADOW_ENABLED")` mechanism. At authenticated D06 launch, a nonempty `tenant_id` is captured in trusted server-side run state keyed by `run_id`; it is never placed in the manifest or a client payload/query. The existing headerless EventSource stream must never be made to require an authorization header. Instead, the stream/runner obtains the captured tenant only from that trusted server-side run state and passes it to the daemon worker. The feature-flag lookup occurs inside the worker, never on the D06 runner/caller path. There is no bootstrap/default-tenant fallback for this adapter: absent/invalid tenant context or flag-service failure disables shadow work.

The flag defaults off and is excluded from the frozen manifest, `manifest_fingerprint`, D06 methodology/reconciliation identity inputs, source-artifact references, report identity, readiness, API, and UI. Enabling or disabling it must leave D06 rows and AAR artifact payloads, identities, hashes, lineage, and lifecycle byte/row identical for the same frozen run.

## Telemetry, privacy, and retention

Telemetry is fail-open and has two distinct channels.

1. The initial transport is existing structured application logging. `d06_dsc_cadence_shadow_metric_v1` is a low-cardinality operational metric only: adapter version, closed outcome, closed reason category, a bounded elapsed-time bucket, and whether the flag was enabled. It contains no run/asset/snapshot/table/column/tenant identifiers, artifact IDs/hashes, values, paths, exception text, parser detail, per-entity counts, candidate counts, or cadence interval class.
2. Reproducibility uses the consumer-owned, access-controlled `d06_dsc_cadence_shadow_audits` table. It is not a general application log, analytics event, AAR artifact, or generic API resource. Its required identity is `tenant_id`, `run_id`, and `adapter_version`, with `UNIQUE(run_id, adapter_version)` and atomic insert-ignore semantics. Its sanitized payload may contain the frozen run reference, snapshot/table identity, exact selected qualified columns, `resolved_as_of`, outcome/reason, and assertion artifact ID/hash/dependency fingerprint. It excludes raw values, source paths, exception text, parser diagnostics, samples, row-level data, and per-entity counts. Exact IDs and hashes are forbidden outside this access-controlled audit table.

The audit table has dedicated tenant-scoped service access only: no generic AAR/diagnostic list/detail/payload route may expose it. Its deletion is coupled to existing run deletion, item deletion, and factory-reset cleanup paths, each constrained by `tenant_id`; it has no independent public retention action. If audit insertion is unavailable, busy, over deadline, or fails, no audit row is written and the metric attempt/failure remains fail-open. The initial log channel uses the existing application-log policy; the audit table uses its tenant-scoped cleanup/access policy. Both have at most one metric and one insert-ignore audit attempt per D06 execution, with only closed-enum labels.

## Invariance obligation

With the flag both off and on—under `supports`, every other closed outcome, seam timeout/exception, and telemetry failure—the implementation must prove:

1. Frozen manifest JSON and `manifest_fingerprint` are byte-identical before and after the attempted observation.
2. D06 reconciliation identity inputs, methodology fingerprint, source references, AAR payload bytes/hashes, artifact rows/identities, lineage/lifecycle rows, reuse disposition, rules, findings, and results are complete before scheduling and identical to the baseline for the same frozen run.
3. Readiness, manifest/API/UI schemas and responses, controls, role confirmation, completed run events, and finding/disposition workflow contain no shadow state and are identical to baseline. The runner return path does not await or expose shadow completion.
4. `report_payload()`/report rendering inputs and resulting report payload/hash are byte-identical when invoked before shadow launch, while the task is running, after completion, or when it never runs.
5. The projection seam itself leaves AAR assertion/context rows, payload bytes/hashes, events, status rows, and lifecycle unchanged. The only permitted shadow write is the separate consumer audit-table insert-ignore; it cannot alter D06 or AAR rows.

This is observational equivalence. It does not require D06 and DSC parsers to agree.

## Rollout, rollback, and acceptance tests

Rollout remains disabled until this contract and tests are approved. Enable only for a controlled tenant, inspect only the bounded metric/audit channels, and require paired golden runs to meet the invariance obligation. A future change that pins DSC references in D06 or affects a manifest, readiness, UI, or execution needs a separate versioned adoption contract; shadow observations are not adoption authority.

Rollback is immediate by disabling `D06_DSC_CADENCE_SHADOW_ENABLED` for the tenant. It needs no repair or migration because the shadow path changes neither D06 nor AAR state.

Acceptance tests must prove:

1. Scheduling occurs only after successful authoritative D06 runner writes (reconciliation, results/findings, and AAR persistence), not lazy report generation; the captured input is immutable; thread preparation/start is independently fail-open; and the runner returns without joining. Production scheduling is daemon/background and the direct adapter remains synchronously testable.
2. Authenticated launch captures tenant only in trusted server-side run state; a headerless EventSource stream never requires auth and obtains tenant only through that run state, never a manifest/client query. The worker performs flag lookup only after start. Flag absence, false, tenant isolation, and flag-service fault exit without projection/audit work; invalid/missing tenant disables shadow work; enabled state remains excluded from every D06 identity input.
3. The worker's two-second cooperative deadline, 100 ms total database connection/flag/projection/audit bound, process-exit abandonment, stale-marker expiry, and every worker/log/audit failure produce zero synchronous D06 latency and cannot alter completed D06 execution or indefinitely suppress later shadow runs.
4. The seam rejects broad selectors; uses one consistent transaction and structured `resolved_as_of` timestamp/read-boundary fingerprint over exact selected pins and catalogue/lifecycle marker; never uses `PRAGMA data_version`; returns closed response identity/reasons; uses SQL `LIMIT 5` for four candidates; enforces the 16-reference, payload-byte, and evidence-record caps; verifies hashes without mutation; and performs no source/raw/profile/producer access or context/assertion/event/status/lifecycle write, truncation, or retry.
5. An assertion for another axis, grouping, table, snapshot, or composite grouping is ignored rather than selected; the exact selected pair is absent when no exact locator exists.
6. Sole observed and agreeing confirmed assertions, unknown assertions with full reconstructable producer provenance, competing observations/confirmations, mismatched confirmation dependencies, tampered pins, and lifecycle/dependency changes yield precisely the specified projection/comparison outcomes; incomplete/invalid unknown provenance is unavailable.
7. Every interval mapping above yields `supports`; mapped non-equality yields `different_observed_interval`; mixed, irregular, and unmapped regular classes yield `non_regular`; parser divergence is advisory only.
8. Each closed outcome, timeout, malformed response, seam error, log failure, audit failure, and process exit leaves already-completed D06 reconciliation byte/row identical; reports generated before, during, after, or without shadow are byte-identical.
9. Metric/audit payloads obey their separate privacy and cardinality contracts; the audit table permits one atomic insert-ignore row per `(run_id, adapter_version)`, is tenant scoped/no generic API exposure, and participates in run/item/factory cleanup. Artifact IDs/hashes appear only in its access-controlled fixture.
